# System Audit Skill - 使用範例

## 範例 1：基本系統審查

**場景**：對當前專案進行完整審查

```
使用者：「對這個專案做系統審查」

Agent 會：
1. 讀取 D:/Source/skills/system-audit/SKILL.md
2. 讀取 D:/Source/skills/system-audit/config/audit-scoring.yaml
3. 對當前專案進行 7 維度、38 子項評估
4. 產出報告到 reports/audit-{project}-{date}.md
```

**預期輸出**：
```markdown
# 系統審查報告

## 基本資訊
| 項目 | 值 |
|------|---|
| 目標系統 | my-project |
| 系統路徑 | /path/to/my-project |
| 審查日期 | 2026-02-16 |
| 權重模型 | balanced |
| 審查者 | Claude Code (system-audit skill v1.0.0) |

## 總覽
| 維度 | 權重 | 得分 | 等級 |
|------|------|------|------|
| 資訊安全 | 20% | 75/100 | B |
| 系統架構 | 18% | 82/100 | A |
| 系統品質 | 18% | 68/100 | C |
...
| **加權總分** | **100%** | **74.5/100** | **B** |
```

## 範例 2：安全優先模式審查

**場景**：對金融/醫療系統使用安全優先權重

```
使用者：「用安全優先模式審查這個系統」

Agent 會：
1. 讀取 audit-scoring.yaml 的 security_first 權重
   - 資訊安全：30%（vs balanced 20%）
   - 系統架構：15%（vs balanced 18%）
   - ...
2. 以安全為重點進行評估
```

**適用情境**：
- 金融支付系統
- 醫療健康資料系統
- 政府敏感資料系統
- 身份驗證服務

## 範例 6：定期審查（追蹤趨勢）

**場景**：每月執行一次，追蹤進步

**第一次審查**（2026-01-16）：
```
總分：68/100（C 級，及格）
- 資訊安全：60（無 Hook 保護）
- 系統品質：55（測試覆蓋率 30%）
```

**第二次審查**（2026-02-16）：
```
總分：74/100（B 級，良好）✅ +6 分
- 資訊安全：75（新增 Hook 攔截）✅ +15
- 系統品質：68（測試覆蓋率 50%）✅ +13
```

**建議**：
- 將歷史報告保存在 `reports/` 目錄
- 用 git 追蹤報告變化
- 設定目標：每月提升 5-10 分

## 範例 7：整合到 CI/CD

**場景**：Pull Request 前自動審查

**GitHub Actions 範例**：
```yaml
name: System Audit

on:
  pull_request:
    branches: [main]

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Run System Audit
        run: |
          # 觸發 Claude Agent 執行審查
          claude -p "對這個專案做系統審查，只接受 B 級以上"

      - name: Check Audit Result
        run: |
          # 解析報告，檢查分數
          score=$(grep "加權總分" reports/audit-*.md | cut -d'|' -f5)
          if [ $score -lt 70 ]; then
            echo "審查失敗：分數 $score < 70"
            exit 1
          fi
```

## 範例 9：交付前品質閘門

**場景**：確保交付品質達標

```
使用者：「這個系統是否達到交付標準？最低要求 B 級（70 分）」

Agent 會：
1. 執行完整審查
2. 檢查總分是否 ≥ 70
3. 檢查是否有 F 級維度（嚴重缺陷）
4. 檢查校準規則是否觸發（如：硬編碼密碼）
5. 輸出 PASS/FAIL 判定
```

**PASS 範例**：
```
✅ 總分：74/100（B 級）
✅ 無 F 級維度
✅ 無觸發校準上限
→ 品質閘門：PASS，可交付
```

**FAIL 範例**：
```
❌ 總分：68/100（C 級，未達 70）
❌ 資訊安全：38/100（F 級，硬編碼密碼）
❌ 觸發校準：無測試 → 品質上限 50
→ 品質閘門：FAIL，需改善後重審
```

**場景**：團隊成員各自審查不同維度

**分工**：

```
「只評估技術棧、系統文件、系統完成度維度」
```

## 進階用法：自訂校準規則

如果預設校準規則不符合需求，可以修改 `config/audit-scoring.yaml`：

```yaml
calibration:
  rules:
    - "無自動化測試 → 系統品質上限 50"
    - "無安全掃描/Hook → 資訊安全上限 60"
    - "TODO/FIXME > 20 → 系統完成度上限 50"
    # 新增自訂規則
    - "無 CI/CD → 系統工作流上限 65"
    - "無 API 文件 → 系統文件上限 55"
```

## 常見問題

### Q1: 審查需要多久？
- **互動式手動審查**：15-30 分鐘（取決於專案大小）
- **自動排程團隊模式**：15-20 分鐘（並行加速）

### Q2: 審查會修改程式碼嗎？
- **預設不會**：僅評估和產出報告
- **團隊模式可選**：可自動修正簡單問題（如新增配置檔、更新文件），但需明確啟用

### Q3: 如何提高分數？
1. 參考報告中的「TOP 5 改善建議」
2. 優先處理 F/D 級維度
3. 關注觸發校準上限的項目（如：新增測試、移除硬編碼密碼）

### Q4: 可以審查非程式碼專案嗎？
- **可以**，但某些維度會評估為 N/A（如：文件專案無程式碼品質維度）
- N/A 項目的權重會自動重分配給其他子項

### Q5: 評分是否客觀？
- **相對客觀**：基於具體證據（檔案路徑、Grep 結果、指令輸出）
- **需校準**：預設校準規則防止虛假高分，可根據組織標準調整
- **僅供參考**：最終品質需結合專案背景判斷
